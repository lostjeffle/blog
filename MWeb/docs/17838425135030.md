title:'page pining'
## page pining

### get_user_pages() 的作用

#### 访问页的物理地址

在处理 O_DIRECT IO 时，（对于 block based filesystem）通常由硬件 DMA 设备实现用户虚拟地址到后端存储之间的数据搬运，而 DMA 设备只识别物理地址（例如 DMA 只识别 struct page 描述符组成的 sg list），因而 get_user_pages() 的一个主要作用就是将输入的用户虚拟地址（通过用户进程的页表）翻译成 struct page 描述符（这一过程包括走一遍页表流程、有时还会伴随 page fault）

```c
/*
 * @start:      starting user address
 * @pages:      array that receives pointers to the pages pinned.
 */
long get_user_pages(unsigned long start, unsigned long nr_pages,
		    unsigned int gup_flags, struct page **pages)
```

> 由于需要使用用户进程的页表来实现上述翻译，因而必须在对应用户进程的上下文中调用 get_user_pages() 接口。此外当用户进程遭受到 fatal signal (e.g. SIGKILL) 的时候，该接口还会提前返回报 EAGAIN、EINTR 等错误。


除了 O_DIRECT IO 场景 DMA 需要访问用户页的物理地址以外，另外一个场景是“跨进程访问用户页”，其典型场景是 FUSE 的 O_DIRECT IO 场景。FUSE 在处理 O_DIRECT IO 时，其数据搬运完全是 CPU memcpy 并不涉及 DMA 操作，因而直观上会觉得并不需要 get_user_pages() 接口，但是 FUSE 的特殊之处在于：

- 用户进程对 FUSE 文件发起一个 O_DIRECT IO 操作
- 在 FUSE 的实现中，最终执行 O_DIRECT IO 数据搬运操作的，是在 FUSE daemon 进程的上下文中，而非当初发起这个 O_DIRECT IO 的用户进程的上下文。由于 copy_[from|to]_user() 这类接口依赖页表才能访问页内存，FUSE daemon 进程上下文中不能直接访问 O_DIRECT IO 传入的用户虚拟地址

因而当前 FUSE O_DIRECT IO 实现过程中，用户进程在发起 FUSE O_DIRECT IO 的时候，会在用户进程上下文（下发 O_DIRECT IO 过程中）调用 get_user_pages() 接口将需要执行 O_DIRECT IO 的用户虚拟地址翻译为 struct page 描述符；之后 FUSE daemon 在处理 O_DIRECT IO 的时候接收到的是 struct page 描述符，因而就可以在 FUSE daemon 进程上下文中访问目标内存页



#### page pining 语义

除了将用户虚拟地址翻译成 struct page 描述符以外，get_user_pages() 接口提供的另一个重要语义是将这个页 pin 住，防止其被换出（swap）、回收（reclaim）、迁移（migrate）、COW 等

考虑执行 O_DIRECT IO 过程中，DMA 硬件使用用户页的物理地址对用户页进行数据搬运，在 DMA 完成之前要求用户页必须保持有效、并且物理地址保持不变。试想以下几个场景：

- 用户页被换出（swap）（e.g. 用户进程的 anonymous mapping 内存）
- 用户页被回收（reclaim）（e.g. O_DIRECT IO 传入的虚拟地址是另一个文件的 file mapping 地址）
- 用户页被迁移（migrate）
- 用户页发生 COW 

上述场景用户页的物理地址都会发生变化。为了解决这一问题，get_user_pages() 接口提供的一个重要语义就是将这个页 pin 住，从而防止对应的页被换出（swap）、回收（reclaim）、迁移（migrate）、COW 等


接下来看一下 page pining 的语义是如何实现的

> get_user_pages

首先在 get_user_pages() 侧实际上就只是将 page 的 _refcount 引用增加 1

```
# @gup_flags contains FOLL_GET
get_user_pages(..., gup_flags, ...)
    gup_flags |= FOLL_TOUCH
    __get_user_pages_locked
        __get_user_pages
            follow_page_mask
                follow_p4d_mask
                    follow_pud_mask
                        follow_pmd_mask
                            follow_page_pte
                                try_grab_folio(page_folio(page), 1, FOLL_GET)
                                    folio_ref_add(folio, 1)
                                        page_ref_add(&folio->page, 1)
                                            # increment 1 refcount on the head page of the folio
```

```c
struct page {
    atomic_t _refcount;
    ...
}
```

> 换出（swap）

swap 路径中会检查当前尝试换出的页，其引用计数是否是预期的 "1 + folio_nr_pages(folio)"

- 1 引用，回收流程自己持有的那一个引用 (isolate 时拿的) 
- folio_nr_pages(folio) 引用，folio 中的每个 page 对于 folio 持有一个引用

即当前没有其他代码对该页持有引用，那么就认为这个页是空闲的可以被换出；否则其他地方（例如get_user_pages()）还持有对页的引用，此时就不能将这个页换出

```
# kswapd
try_to_free_pages
    do_try_to_free_pages
        shrink_zones
            shrink_node
                shrink_node_memcgs
                    shrink_lruvec
                        shrink_list
                            shrink_inactive_list
                                shrink_folio_list
                                    add_to_swap(folio) # allocate folio to swap cache
                                        add_to_swap_cache
                                            folio_set_swapcache(folio)
                                        folio_mark_dirty(folio)
                                        
                                    try_to_unmap # remove page table mapping
                                    pageout(folio, ...) # write to swap cache
                                   
                                    mapping = folio_mapping(folio)
                                        # if folio_test_swapcache(folio):
                                            return swap_address_space(folio->swap)
                                    
                                    # since mapping is not NULL:
                                    __remove_mapping(mapping, folio, ...)
                                        refcount = 1 + folio_nr_pages(folio)
                                        if !folio_ref_freeze(folio, refcount):
                                            goto cannot_free
```


> 回收（reclaim）

reclaim 路径的处理是类似的，如果当前尝试回收的页，其引用计数不是预期的 "1 + folio_nr_pages(folio)"，就说明其他地方（例如get_user_pages()）还持有对页的引用，此时就不能将这个页回收

```
# reclaim
try_to_free_pages
    do_try_to_free_pages
        shrink_zones
            shrink_node
                shrink_node_memcgs
                    shrink_lruvec
                        shrink_list
                            shrink_inactive_list
                                shrink_folio_list
                                        
                                    try_to_unmap # remove page table mapping
                                    pageout(folio, ...) # write to swap cache
                                   
                                    mapping = folio_mapping(folio)
                                    # since mapping is not NULL:
                                    __remove_mapping(mapping, folio, ...)
                                        refcount = 1 + folio_nr_pages(folio)
                                        if !folio_ref_freeze(folio, refcount):
                                            goto cannot_free
```

> 迁移（migrate）

类似地，迁移（migrate）路径中如果当前尝试迁移的页，其引用计数不是预期的 "1 + folio_nr_pages(folio)"，就说明其他地方（例如get_user_pages()）还持有对页的引用，此时就不能迁移这个页

```
migrate_pages(&cc->migratepages, ...)
    # do async migration
    migrate_pages_batch(..., MIGRATE_ASYNC, ...)
        # 1. remove mapping for all src pages
        # for each folio in cc->migratepages list:
            migrate_folio_unmap
                # 1.1 alloc dst folio
                compaction_alloc
                    # alloc dst folio from cc->freepages[order] list,
                    # refill cc->freepages[order] list (if empty) by scanning
                    # whole zone to find all free pages
                
                # 1.2 lock src folio
                    # if trylock failed (in async migration), return -EBUSY
                    
                # 1.3 ensure folio is not under writeback
                    # if folio is under writeback (in async migration),
                    # don't wait for writeback IO completion and return -EBUSY
                
                # 1.4 replace all page table mappings with swap entries
                try_to_migrate
                
                
        # 2. move src folio to dst folio
        # for each previously unmapped page:
            migrate_folio_move(..., src, dst, ...)
                move_to_new_folio
                    # if src folio is page cache:
                        a_ops->migrate_folio(..., dst, src, ...), e.g. filemap_migrate_folio()
                            folio_migrate_mapping(..., 0)
                                expected_count = folio_expected_refs(mapping, folio)
                                    # for page cache:
                                    return folio_nr_pages(folio) + 1;
                                if !folio_ref_freeze(folio, expected_count):
                                    return -EAGAIN   
```


#### page pining 的问题

以上介绍了 get_user_pages() 侧通过简单增加 page->_refcount 引用计数的方法，可以防止 pin 住的页被换出（swap）、回收（reclaim）、迁移（migrate），但阻止不了页被 COW，历史上 GUP+COW 有一个经典的 BUG：

首先复习一下进程 fork 时匿名页 COW 的语义：进程 fork() 时，不会立即复制父进程的匿名私有页给子进程，而是让父子进程的页表 PTE 都指向同一个物理页、并把两边的 PTE 都标成只读、page->_mapcount 计数相应增加。之后任意一方写这个页 → 触发写保护缺页 → COW 处理:分配新页、复制内容、让写方的 PTE 指向新页并置可写。这样父子从此各持一份,互不影响。这个机制的正确性依赖一个假设:页表映射是访问这个物理页的唯一途径。但是 GUP 打破了这个假设，例如：

```
进程 A 有匿名私有页 P, get_user_pages() 让硬件长期持有 P(比如网卡收包写入 buffer)。然后 A fork() 出子进程 B。此刻 P 被父子共享、置只读。后续有两种可能：

case 1:如果子进程先写
   1. B 写 P → COW 触发 → B 分配新页 P',复制内容,B 的 PTE 指向 P',P 的 mapcount 降回 1(只剩 A);
   2. A 继续持有 P,硬件也继续往 P 里 DMA 写数据;
   3. 结果:A 能看到硬件写入的数据(正确)，这个 case 是符合预期的。

case 2:如果父进程(pin 方)先触发写
   1. A 触发 COW → A 得到新页 P',A 的页表指向 P';
   2. 但硬件 DMA 还在往老页 P 写;
   3. A 后续通过页表读到的是 P'(看不到 DMA 新数据), 这就导致 DMA 写进 P 的数据 A 看不到、还泄漏给了还映射着 P 的子进程 B。
```

此时 case 1（预期的）还是 case 2（BUG）完全取决于时序上是父进程还是子进程先触发写


原因是 COW 功能一开始就被设计为支持对仍被引用的页进行迁移（migrate）和 COW。例如当一个页仍然被引用的时候，内存子系统也可以对这个页进行迁移操作，或者说迁移（migrate）本来就是用来对仍在引用的页进行迁移的

为了解决上述问题，需要引入另外一种引用计数（与原来的 page->_refcount 引用计数区分开）来描述“页的物理地址当前正在被引用、因而不能对页进行迁移（migrate）、COW”这一情况，因而 get_user_pages() 引入了 FOLL_GET、FOLL_PIN 这两个标志

FOLL_GET 描述有人正在引用这个页，这种引用往往是临时的、短期的、只是为了防止这个页被释放，例如 get_page()/put_page() 就是用来短暂地持有这种引用，原来 get_user_pages() 的默认行为即为 FOLL_GET，即只是给 page->_refcount 引用计数加 1，可以防止页被换出（swap）、回收（reclaim）、迁移（migrate）

新引入的 FOLL_PIN 则用于描述页的物理地址正在被引用、整个物理页被 pin 住（从而防止页被 COW）的情况。在实现上，由于 struct page 描述符本身没有多余的其他字段来承载这个新的引用计数，因而新引用计数仍然复用原来的 page->_refcount 字段，只是使用 +1024 bias，即新引用计数加 1 相当于 page->_refcount 字段加 1024

此时引入了新的 pin_user_pages() 接口来描述这种语义

```c
/*
 * @start:	starting user address
 * @pages:	array that receives pointers to the pages pinned.
 */
long pin_user_pages(unsigned long start, unsigned long nr_pages,
		    unsigned int gup_flags, struct page **pages)
```

```
pin_user_pages(..., gup_flags, ...)
    gup_flags |= FOLL_PIN
    __gup_longterm_locked
        __get_user_pages_locked
            __get_user_pages
                follow_page_mask
                    follow_p4d_mask
                        follow_pud_mask
                            follow_pmd_mask
                                follow_page_pte
                                    try_grab_folio(page_folio(page), 1, FOLL_PIN)
                                        folio_ref_add(folio, GUP_PIN_COUNTING_BIAS)
                                            page_ref_add(&folio->page, GUP_PIN_COUNTING_BIAS)
                                                # increment 1024 refcount on the page
```


同时引入 page_maybe_dma_pinned() 接口来判断给定的页是否是 FOLL_PIN 住的

```c
bool page_maybe_dma_pinned(struct page *page)
```

```
page_maybe_dma_pinned
    folio_maybe_dma_pinned(page_folio(page))
        return folio_ref_count(folio)) >= GUP_PIN_COUNTING_BIAS
```


> COW

此时 fork() 流程中如果发现父进程的匿名页是被 pin 住（page_maybe_dma_pinned() 为 true）的，就会立即为子进程分配一份 copy，这样之前 GUP 返回的物理页仍然指向父进程的那一份匿名页，从而修复了 GUP+COW BUG

```
kernel_clone
    copy_mm
        dup_mmap
            copy_page_range
                copy_p4d_range
                    copy_pud_range
                        copy_pmd_range
                            copy_pte_range
                                copy_present_ptes
                                    # for anonymous page:
                                    folio_try_dup_anon_rmap_pte
                                        __folio_try_dup_anon_rmap
                                            maybe_pinned = folio_needs_cow_for_dma()
                                                return folio_maybe_dma_pinned(folio)
                                            if maybe_pinned:
                                                return -EBUSY
                                    
                                    # Page may be pinned, we have to copy
                                    copy_present_page
                                        # copy for child process
```


#### page pining 的优化：FOLL_LONGTERM

page pining 总的框架大致就是如此，总的来说就是通过

- FOLL_GET 描述"对 struct page 的临时引用"，例如 get_page()，可以防止页被换出（swap）、回收（reclaim）、迁移（migrate）
- FOLL_PIN 描述页的物理地址正在被引用、整个物理页被 pin 住的情况，从而防止页被换出（swap）、回收（reclaim）、迁移（migrate）、COW。

但是 FOLL_PIN 这种 pin 是相对短暂的情况，例如一次 O_DIRECT IO、或者一次 DMA 操作完成后就会被 unpin。如果一个用户页的物理页被长时间地 pin 住，就会导致这个页长时间无法执行迁移（migrate）操作，从而影响大块连续物理内存或者 CMA 的正常运行。为了优化这个问题，在 FOLL_PIN 的基础上引入 FOLL_LONGTERM

- FOLL_PIN+FOLL_LONGTERM 描述整个物理页被**长时间** pin 住，例如长时间作为 DMA 的目标缓存区，此时在 pin_user_pages(..., FOLL_PIN+FOLL_LONGTERM) 流程中就会将这个页从 MOVABLE zone 事先迁移到 UNMOVABLE zone，从而避免后续这个页无法被迁移的情况

```
pin_user_pages(..., gup_flags, ...)
    gup_flags |= FOLL_PIN
    __gup_longterm_locked
        __get_user_pages_locked
            __get_user_pages
                follow_page_mask
                    follow_p4d_mask
                        follow_pud_mask
                            follow_pmd_mask
                                follow_page_pte
                                    try_grab_folio(page_folio(page), 1, FOLL_PIN)
                                        folio_ref_add(folio, GUP_PIN_COUNTING_BIAS)
                                            page_ref_add(&folio->page, GUP_PIN_COUNTING_BIAS)
                                                # increment 1024 refcount on the page

        check_and_migrate_movable_pages
            migrate_longterm_unpinnable_pages
                # for movable pined pages:
                migrate_pages
```


#### page pining 的优化：page_maybe_dma_pinned() 优化

以上介绍到，FOLL_PIN 语义需要引入一个新的引用计数（与原来的 page->_refcount 引用计数区分开），但是在实现上由于 struct page 描述符本身没有多余的其他字段来承载这个新的引用计数，因而新引用计数仍然复用原来的 page->_refcount 字段，只是使用 +1024 bias；同时 page_maybe_dma_pinned() 检查到 page->_refcount 引用计数 达到 1024 时，即认为这个 page “可能” 是被 pin 住的

这里的“可能”是因为两个引用计数语义复用同一个 page->_refcount 字段，如果 get_page() 超过 1024 次，page_maybe_dma_pinned() 就会触发 false positive，带来的结果就是 fork() 流程中为子进程分配了 copy，而这本来是不需要的，也就是这个导致了性能上的次优，而非 BUG

因而对于以上问题的一个优化是，对于 large folio，可以复用 large folio 中第二个 page 的 mapping、index 这些字段，用于存储这个新的引用计数，即 folio->_pincount

```c
struct folio {
    union {
        struct page page;
    };
    
    union {
        struct {
            atomic_t _pincount;
            ...
        };
        struct page __page_1;
    }
}
```

此时 pin_user_pages() 中 head page 的  page->_refcount 计数就只会增加 1，同时 folio->_pincount 计数增加 1

```
pin_user_pages(..., gup_flags, ...)
    gup_flags |= FOLL_PIN
    __gup_longterm_locked
        __get_user_pages_locked
            __get_user_pages
                follow_page_mask
                    follow_p4d_mask
                        follow_pud_mask
                            follow_pmd_mask
                                follow_page_pte
                                    try_grab_folio(page_folio(page), 1, FOLL_PIN)
                                        # for large folio:
                                        folio_ref_add(folio, 1)
                                        atomic_add(refs, &folio->_pincount)
```


此时 page_maybe_dma_pinned() 中就不会触发 false positive

```
page_maybe_dma_pinned
    folio_maybe_dma_pinned(page_folio(page))
        # for large folio
        return atomic_read(&folio->_pincount) > 0
```
