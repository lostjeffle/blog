## firecracker - memfile

[Firecracker Snapshotting](https://github.com/firecracker-microvm/firecracker/blob/main/docs/snapshotting/snapshot-support.md)

### create snapshot

`/snapshot/create` API 用于创建快照，`snapshot_type` 可以为 Full 或者 Diff

```
curl --unix-socket /tmp/firecracker.socket -i \
    -X PUT 'http://localhost/snapshot/create' \
    -H  'Accept: application/json' \
    -H  'Content-Type: application/json' \
    -d '{
            "snapshot_type": "Full",
            "snapshot_path": "./snapshot_file",
            "mem_file_path": "./mem_file"
    }'
```

### load snapshot

`/snapshot/load` API 用于从快照恢复 microVM

```
curl --unix-socket /tmp/firecracker.socket -i \
    -X PUT 'http://localhost/snapshot/load' \
    -H  'Accept: application/json' \
    -H  'Content-Type: application/json' \
    -d '{
            "snapshot_path": "./snapshot_file",
            "mem_backend": {
                "backend_path": "./mem_file",
                "backend_type": "File"
            },
            "track_dirty_pages": true,
            "resume_vm": false
    }'
```

- backend_type 为 File，此时 backend_path 描述 memfile 文件的路径
- backend_type 为 Uffd，此时 backend_path 描述一个 domain socket 路径，VMM (Firecracker) 进程与 Uffd handler 进程之间就通过这个 UDS 进行通讯


### hugetlbfs

- cold boot

```
curl --unix-socket /tmp/firecracker.socket -i  \
    -X PUT 'http://localhost/machine-config' \
    -H 'Accept: application/json'            \
    -H 'Content-Type: application/json'      \
    -d '{
            "huge_pages": 2M,
            ...
    }'
```

如果 `/machine-config` 请求中指定 `huge_pages=2M`，那么 microVM 第一次冷启动时，firecracker 的 guest 内存实现为对 host hugetlb 的 mmap 映射

```
VmResources::allocate_guest_memory
    allocate_memory_regions
        mmap(MAP_PRIVATE | MAP_ANONYMOUS | MAP_HUGETLB | MAP_HUGE_2MB | MAP_NORESERVE)
```

mmap(MAP_PRIVATE | MAP_ANONYMOUS ...) 系统调用内部会分配一个 hugetlbfs 的匿名 inode，此时 VMM 对该 mmap(MAP_PRIVATE | MAP_ANONYMOUS ...) 映射区间的访问，实际就转换为类似 hugetlbfs 的文件映射，发生 page fault 的时候就直接从 hugetlb 分配一个大页，从而减小 VMM 的 page fault 次数以及 host 上 TLB 竞争


- dump snapshot

按照正常流程将 guest memory 保存为一个 memfile 文件


- load from snapshot

从 memfile 快照恢复同时要走 hugetlbfs 路径时，`backend_type` 不能是 file，这是因为 MAP_HUGETLB 只对 hugetlbfs/shmem(MFD_HUGETLB) 生效，普通文件无法执行 MAP_HUGETLB；因而 huge_pages=2M dump 下来的快照在恢复时 backend_type 必须走 uffd 路径

```
guest_memory_from_uffd
    create_guest_memory
        page_size: huge_pages.page_size(),  // = 2MB,随 domain socket 握手协议下发
    uffd.register(region) // 注册 2MB page size 的内存布局
```

随后就都是 2MB 粒度的 page fault 了：

- 缺页上报粒度：hugetlb VMA 上的 uffd 事件，uffd_msg.address 按 2MB 对齐——guest 访问 hugepage 内任意 4K 子页，上报的都是整页起始地址；
- UFFDIO_COPY 模式：外部 handler 必须一次提供完整的 2MB 数据（src 缓冲区 2MB 对齐、长度恰为 2MB），从 memfile 的 region.offset + 页内偏移处读取；
- Zero-copy 模式（本分支 uffd_block.rs）：page_size 经 VmaRegion 下发给 server（uffd_block.rs:162），server 返回的 blob fd 必须是 hugetlbfs/shmem 且大小匹配，随后 VMM 接收到 blob fd 后执行 mmap(target_addr, len, prot, flags | MAP_FIXED, blob_fd, blob_offset) 才能把 2MB 页整体 MAP_FIXED 覆盖到 fault 区域


### Transparent Huge Pages (THP)

- cold boot

```
curl --unix-socket /tmp/firecracker.socket -i  \
    -X PUT 'http://localhost/machine-config' \
    -H 'Accept: application/json'            \
    -H 'Content-Type: application/json'      \
    -d '{
            "huge_pages": Transparent,
            ...
    }'
```

如果 `/machine-config` 请求中指定 `huge_pages=Transparent`，那么 microVM 第一次冷启动时，firecracker 的 guest 内存是普通的匿名映射，但是会对映射区间执行 MADV_HUGEPAGE madvise(2)

```
VmResources::allocate_guest_memory
    allocate_memory_regions
        mmap(MAP_PRIVATE | MAP_ANONYMOUS | MAP_NORESERVE)
        madvise(..., MADV_HUGEPAGE)
```

随后匿名映射发生 page fault 时，内核就会优先分配大页


- dump snapshot

按照正常流程将 guest memory 保存为一个 memfile 文件


- load from snapshot

从 memfile 快照恢复同时要走 THP 路径时，`backend_type` 可以设置为 file，此时 memfile 文件映射发生 page fault 时，如果对应的文件系统实现有 vm_ops.huge_fault()，内核就会优先分配大页
